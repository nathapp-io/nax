**Author:** investigation from prompt audit + run logs of `retry-strategy-consolidation`

## TL;DR

PR 3.1 (ADR-022 phase 5, landed 2026-05-03) wired the `priorAdversarialIterations` carry-forward end-to-end, but the goalpost-moving symptom from #736 still occurs. Two concrete defects:

1. **Block content is count-only.** The rendered table shows `1 [test-gap]` instead of the actual finding text — the reviewer cannot judge whether prior findings were addressed.
2. **Carry-forward dies on autofix re-entry.** State lives on `PipelineContext` (attempt-scoped); when `cycle exited — agent gave up` triggers a fresh TDD attempt, prior iterations vanish even within the same run.

This document plans two small patches to fix both defects (`3.1.1` and `3.1.2`), gates PR 3.2 / 3.3 on a second telemetry pass, and pulls semantic-review parity into scope.

## Defect 1 — Block content is too compressed

### Where

`src/prompts/builders/prior-iterations-builder.ts:32-67`. The table cell shows `<count> [<top-category>]`. The actual `findingsBefore[].message / file / line / suggestion / meta.acQuote` are dropped.

### Why it produces goalpost-moving

The reviewer sees that *some* test-gap was flagged but nothing about *which* test-gap. When it scans the diff fresh on round N+1, nothing prevents it from:

- Flagging a *different* test-gap and treating it as a new finding.
- Re-flagging the same one with new wording, defeating de-duplication.
- Silently dropping a still-valid finding because the count column doesn't force re-confrontation.

This matches the audit: US-005b R1→R2 within Run 2 had the block, and R2 produced an entirely disjoint finding set.

The issue body specified the block as "`## PRIOR ADVERSARIAL FINDINGS — Round N-1` block with a verdict-first instruction". The implementation preserved the header and outcome column but compressed away the findings — that compression is what makes it inert.

## Defect 2 — Carry-forward dies on attempt re-entry

### Where

`src/pipeline/types.ts:258` — `priorAdversarialIterations?: Iteration[]` is on `PipelineContext`. `src/review/orchestrator.ts:601-625` reads/writes it via `ctx`.

### Why it produces goalpost-moving

`PipelineContext` lifetime is one execution attempt. Two paths reset it within a single run:

1. **`cycle exited — agent gave up`** triggers a new TDD attempt with a fresh ctx. Observed Run 3 R3 → R4: same RunId `cf98f737-…`, two adversarial reviews 14 minutes apart, R4 prompt has no prior block.
2. **Cross-process restart** of the same feature loses state entirely. Observed Run 2 → Run 3 (US-005b restarted from R3).

The issue body specified "in-memory on `ReviewOrchestrator`, run-scoped" but the implementation chose ctx-scoped. Run-scoped survives case 1; cross-run survival (case 2) requires disk and is out of scope for #736.

## Patch A — Rich block content with verdict template

**File:** `src/prompts/builders/prior-iterations-builder.ts`

### A1. Replace count-summary with per-iteration findings list

```typescript
export function buildPriorIterationsBlock<F extends Finding>(iterations: Iteration<F>[]): string {
  if (iterations.length === 0) return "";

  const sections = iterations.map((iter) => renderIteration(iter));
  const verdictTemplate = renderVerdictTemplate(iterations);

  return [
    "## Prior Iterations — verdict required before new analysis",
    "",
    ...sections,
    "",
    verdictTemplate,
    "",
  ].join("\n");
}

function renderIteration<F extends Finding>(iter: Iteration<F>): string {
  const header = `### Round ${iter.iterationNum} — outcome: ${iter.outcome} (${iter.findingsBefore.length} → ${iter.findingsAfter.length})`;
  if (iter.findingsAfter.length === 0) return [header, "_All prior findings cleared._"].join("\n");

  const lines = iter.findingsAfter.map((f, i) => renderFinding(f, i + 1));
  return [header, "Findings flagged previously:", ...lines].join("\n");
}

function renderFinding<F extends Finding>(f: F, n: number): string {
  // Finding canonical field is `message` (src/findings/types.ts:139), not `issue`.
  // acQuote lives under `meta` after projection (src/review/finding-projection.ts:89).
  const message = truncate(f.message ?? "", 240);
  const suggestion = truncate(f.suggestion ?? "", 200);
  const loc = f.file ? (f.line != null ? `${f.file}:${f.line}` : f.file) : "(workdir-global)";
  const tag = `[${f.severity} / ${f.category}]`;
  const ac = typeof f.meta?.acQuote === "string" ? f.meta.acQuote : undefined;
  const acLine = ac ? `\n   acQuote: "${truncate(ac, 160)}"` : "";
  return `${n}. ${tag} ${loc}\n   Message: ${message}\n   Suggestion: ${suggestion}${acLine}`;
}

function renderVerdictTemplate(iterations: Iteration<Finding>[]): string {
  const total = iterations.reduce((sum, it) => sum + it.findingsAfter.length, 0);
  const hasUnchanged = iterations.some((i) => i.outcome === "unchanged");
  const unchangedNote = hasUnchanged
    ? `\n\nWhen outcome is "unchanged", the prior hypothesis is FALSIFIED — the change did not affect what was tested. Choose a different category before producing a new verdict. Do NOT repeat fixes listed above.`
    : "";

  return [
    `**Required:** before adding any new finding, classify each of the ${total} prior finding(s) above as one of:`,
    `- \`addressed\` — the current diff resolves it (cite the diff line that fixes it in your \`message\` field)`,
    `- \`still-blocking\` — the implementer did not fix it; re-flag it with the IDENTICAL \`file\`, \`line\`, \`category\`, and substantively the same \`message\` wording`,
    `- \`never-an-issue\` — your prior judgment was wrong; explain why in \`message\` and emit severity \`"info"\``,
    `Then surface any genuinely new findings.${unchangedNote}`,
  ].join("\n");
}

function truncate(s: string, max: number): string {
  return s.length > max ? `${s.slice(0, max - 1)}…` : s;
}
```

**LOC delta:** +60 / −35 in this file.

### A2. Token guard

Cap the rendered block at `MAX_BLOCK_CHARS = 6000`. If exceeded, keep the most recent 2 rounds verbatim and collapse older rounds to one-line summaries (`Round 1 — outcome: regressed (3 findings, omitted for brevity)`). Prevents prompt blowup on long runs.

### A3. Tests

`test/unit/prompts/builders/prior-iterations-builder.test.ts` — extend with ~80 LOC:

| Test | Assertion |
|:---|:---|
| `renders empty string for no iterations` | unchanged |
| `renders one round with findings list` | output contains `### Round 1`, `file:line`, `Message:`, `Suggestion:` |
| `renders multiple rounds in order` | rounds appear `### Round 1` … `### Round N` |
| `renders verdict template with correct count` | `${total} prior finding(s)` matches sum of `findingsAfter` |
| `truncates very long message text` | `f.message` > 240 chars ends with `…` |
| `unchanged outcome adds falsified-hypothesis note` | block contains "FALSIFIED" |
| `iterations exceeding budget collapse oldest` | when total > MAX_BLOCK_CHARS, oldest become one-liners |
| `acQuote rendered when present, omitted when absent` | conditional acQuote line |

## Should we proceed to PR 3.2 / 3.3?

**No — gate them on the 2nd-pass telemetry.** Building 3.2 (`priorVerdict[]` field) on top of a block with no findings to verdict is incoherent. 3.3 (convergence-stall escalation) needs the verdict signal from 3.2 to be reliable.

After Patches A + B land and the 2nd-pass telemetry passes, the natural sequence is:

- **3.2 — `priorVerdict[]` response field + implementer feedback loop.** With actual prior text in the prompt, asking the model to emit `addressed/still-blocking/never-an-issue` per prior finding is coherent. The verdict array gives a stable convergence signal and feeds `still-blocking` items into the next implementer prompt (depends on #737 PR 1.2 — already landed, so the dependency is satisfied).
- **3.3 — Convergence-stall escalation heuristic.** Only if 3.2 telemetry shows real stalls (e.g. same finding `still-blocking` 3+ rounds). Without 3.2 we'd escalate on count drift, which the audit proves is unreliable (Run 3 R4 "passed" by severity coincidence; Run 4 caught the unfixed defect).
