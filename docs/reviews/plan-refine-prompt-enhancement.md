# Refine Enhancement Notes

## Context

This note captures what was found while reviewing the `cli-rest` PRD outputs generated by `nax plan` in `refine` mode, plus the code changes made to improve refine quality and failure handling.

Relevant strategy entrypoint:
- `./src/plan/strategies/refine.ts`

The actual leverage points turned out to be:
- `./src/prompts/builders/plan-builder.ts`
- `./src/operations/plan-refine.ts`
- `./src/plan/strategies/write-prd.ts`

## Findings

### 1. `refine` was directionally better than `single`, but its second-turn audit was too narrow

The original refine continuation prompt only checked:
- AC testability
- presence of at least one failure-mode AC
- description/AC contradiction

That improved output quality, but still missed several high-value review dimensions:
- codebase-fit realism
- dependency minimization
- routing realism
- regression coverage
- scope consistency

This gap explained why:
- `prd-refine-01.json` was stronger than `single-*`
- but still did not fully match the best aspects of the more critical `cc` variants

### 2. `refine-02` exposed a new failure mode: internal scope inconsistency

`prd-refine-02.json` improved dependency realism and some codebase-fit details, but introduced inconsistent `Scope` sections such as:
- title/description/ACs clearly included CLI work, while `Scope` said the CLI file was out of scope
- description required `_output.py` helpers, while `Scope` said `_output.py` was out of scope

This showed that refine needed an explicit audit for consistency across:
- title
- description
- scope
- `contextFiles`
- acceptance criteria

### 3. The stricter refine verifier initially over-rejected legitimate ACs

After adding stronger post-refine checks in `plan-refine.ts`, some valid refined drafts were rejected because the observability heuristic was too narrow.

Examples of acceptable AC wording that got rejected:
- "instantiates without raising"
- "invokes provider.refresh_ohlcv(...)"
- "refreshes ALL tickers ..."
- "parses to StopLossTranche(...)"

The problem was not the PRD intent; it was the token heuristic.

### 4. A separate persistence bug could write a raw turn envelope into `prd.json`

When refine verification failed, the run path could fall through to a raw `TurnResult` envelope.

That envelope looked like:

```json
{
  "output": "{ ...actual PRD JSON string... }",
  "tokenUsage": { ... },
  "estimatedCostUsd": ...
}
```

If this reached `writeOrRecoverPrd`, the file could be persisted as if it were a PRD.

This is what caused the broken `prd.json` shape seen during investigation.

## Changes Made

### A. Expanded the second-turn refine audit prompt

File changed:
- `./src/prompts/builders/plan-builder.ts`

Added refine audit sections:
- `codebase-fit`
- `dependency-minimization`
- `routing-realism`
- `regression-coverage`
- `scope-consistency`

Intent:
- make refine compare the draft against the actual codebase context
- remove artificial dependencies
- avoid over-inflated complexity/test strategy
- add backward-compat pressure when changing existing behavior
- catch inconsistent scope statements like those seen in `prd-refine-02.json`

### B. Strengthened post-refine structural verification

File changed:
- `./src/operations/plan-refine.ts`

Added validation logic so refined PRDs are not accepted unless they satisfy structural checks such as:
- each story has at least one negative-path AC
- each story's ACs are observably testable according to a heuristic
- no duplicate dependencies
- no self-dependencies
- no duplicate `contextFiles`
- `contextFiles` length stays within the expected max

Intent:
- stop weak refined drafts from silently passing
- enforce a better floor for refine-mode quality

### C. Relaxed the observability heuristic after false rejections

File changed:
- `./src/operations/plan-refine.ts`

Expanded the observable-token heuristic to accept verbs/patterns like:
- `invokes`
- `refreshes`
- `instantiates`
- `loads`
- `parses`
- `re-constructs` / `reconstructs`

Intent:
- keep the verifier useful without rejecting legitimate behavioral ACs

### D. Hardened PRD persistence/recovery so raw envelopes are not written as PRDs

File changed:
- `./src/plan/strategies/write-prd.ts`

Added extraction logic that:
- first tries to validate a normal PRD object
- then, if the object is actually a raw envelope, tries to parse and validate its `output` field as PRD JSON

Intent:
- prevent `prd.json` corruption when a failed refine attempt falls back to a raw turn result
- recover valid inner PRD JSON when it exists

## Tests Updated

Files changed:
- `./test/unit/prompts/builders/plan-builder.test.ts`
- `./test/unit/operations/plan-refine.test.ts`

What was updated:
- prompt-builder tests now assert the new refine audit sections are present
- refine-operation tests were updated to use refined PRD fixtures that satisfy the stronger verifier contract

## Practical Outcome

Relative to the earlier drafts:
- `refine` output is now better guided on codebase-fit and dependency realism
- refine should be less likely to invent or keep unnecessary dependencies
- refine should be less likely to emit contradictory `Scope` sections
- refine failure should be less likely to corrupt `prd.json`

## Remaining Recommendation

If refine quality still needs improvement after this, the next best enhancement would be:
- add a targeted verifier for `Scope` parsing rather than relying only on prompt pressure
- optionally add soft warnings for suspicious routing inflation or mismatched `Scope`/`contextFiles`
