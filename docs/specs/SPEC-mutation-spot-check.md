# SPEC: Mutation Spot-Check Gate

<!-- spec-writing: completed-through-phase-6 -->

## Summary

After a story reaches GREEN (its tests pass at the `full-suite-gate` phase), nax deterministically mutates a small, bounded number of lines within the story's changed source files, re-runs the story's targeted tests against each mutant, and classifies the result. A **surviving mutant** — one where every test still passes despite an injected bug — produces an **advisory warning** and never blocks the run. The gate is opt-in, deterministic (no LLM), and adds at most `maxMutants` targeted test runs per story. It catches vacuous or over-mocked agent-written tests that the RED gate (`greenfield-gate`) cannot: RED proves tests *exist*, this proves they can *fail meaningfully*.

## Motivation

nax's premise is TDD discipline. The test-writer authors tests first, and `greenfield-gate` (`src/operations/greenfield-gate.ts`) asserts tests exist before implementation. But nothing verifies the tests can fail meaningfully. A test that over-mocks the unit under test, or asserts a tautology, passes GREEN while catching no real bug — a well-documented failure mode of agent-written test suites. Mutation spot-checks close this hole by injecting deterministic bugs into the just-implemented code and confirming the story's own tests notice.

The design deliberately keeps the smallest possible blast radius, consistent with the flaky-quarantine and `nax replay` arcs: a new deterministic operation, a new advisory phase, and one opt-in config sub-tree — no changes to the hot GREEN path, no new LLM calls.

## Design

### Approach — deterministic operators (not LLM)

Mutations are generated by a fixed, language-aware operator table applied to the story's changed source lines. This is the chosen approach over LLM-generated mutations because it is **deterministic and reproducible** (the same run replays identically under `nax replay`), costs **zero tokens**, and is philosophically consistent with nax's existing deterministic gate (`greenfieldGateOp`). The trade-off — occasional equivalent mutants (a mutation that does not change behavior, so tests correctly still pass) — is acceptable precisely because the gate is **advisory**: a false alarm costs one log line, never a blocked story.

A mutant re-run has **three** outcomes, not two — this three-way classification is the primary false-alarm guard:

| `VerificationResult.status` | Outcome | Meaning |
|:--|:--|:--|
| `TEST_FAILURE` | **killed** | A test failed on the mutant → the tests are meaningful. Good. |
| `SUCCESS` | **survived** | All tests passed despite the bug → the advisory warning we emit. |
| `ENVIRONMENTAL_FAILURE` / `ASSET_CHECK_FAILED` / `TIMEOUT` | **errored** | The mutant broke compilation or the runner errored → **inconclusive, discarded**. Never counted as survived. |

### Approach — worked skeleton for the novel op shape

`mutationCheckOp` is a novel shape in this codebase: a `DeterministicOperation` (like `greenfieldGateOp`) that *executes tests* (like `verifyScopedOp`). No existing op combines both. Per the guide, the worked skeleton:

```typescript
// src/operations/mutation-check.ts
// reshapeSelector (src/config/selectors.ts) projects the slice directly, so `.select()`
// returns { enabled, maxMutants, timeoutSeconds } — satisfying US-001 AC-6. A plain
// pickSelector("mutation-check","execution") would return { execution: {...} } instead.
const mutationCheckConfigSelector = reshapeSelector("mutation-check", (c) => c.execution?.mutationCheck);
type MutationCheckConfig = ReturnType<typeof mutationCheckConfigSelector.select>;

export interface MutationCheckInput {
  readonly story: UserStory;
  readonly workdir: string;
  readonly storyId: string;
  readonly packageDir?: string;
  readonly storyGitRef?: string;
  readonly repoRoot?: string;
  readonly packagePrefix?: string;
  readonly resolvedTestPatterns: ResolvedTestPatterns;
}

export interface MutationCheckOutput {
  readonly success: true;                 // advisory — always true
  readonly survivors: readonly SurvivingMutant[];
}

// Injected collaborators (DI, mirrors _verifyScopedDeps) so unit tests need no real git/test run.
export interface MutationCheckDeps {
  detectLanguage: typeof detectLanguage;
  getChangedNonTestFiles: typeof getChangedNonTestFiles;
  selectScopedTests: typeof selectScopedTests;
  regression: typeof regression;
}

export const mutationCheckOp: DeterministicOperation<MutationCheckInput, MutationCheckOutput, MutationCheckConfig> = {
  kind: "deterministic",
  name: "mutation-check",
  stage: "verify",
  config: mutationCheckConfigSelector,
  async execute(input, ctx, deps = _mutationCheckDeps): Promise<MutationCheckOutput> {
    const cfg = /* selected mutationCheck slice */;
    if (!cfg.enabled) return { success: true, survivors: [] };
    const language = await deps.detectLanguage(input.packageDir ?? input.workdir);
    const changed = await deps.getChangedNonTestFiles(
      input.workdir, input.storyGitRef, input.packagePrefix,
      [...input.resolvedTestPatterns.regex], undefined, input.repoRoot,
    );
    const mutants = await generateMutants(changed, language, cfg.maxMutants);
    const survivors: SurvivingMutant[] = [];
    for (const mutant of mutants) {
      await applyMutant(mutant);
      try {
        const scoped = await deps.selectScopedTests({ /* mutant.file, storyGitRef, testCommand, ... */ });
        const result = await deps.regression({ workdir: /* ... */, command: scoped.effectiveCommand, timeoutSeconds: cfg.timeoutSeconds });
        if (classifyMutant(result) === "survived") survivors.push(toSurvivor(mutant));
      } finally {
        await revertMutant(mutant);   // ALWAYS restores, even on throw
      }
    }
    const logger = getLogger();   // from "../logger" — CallContext carries no logger; mirror verifyScopedOp
    for (const s of survivors) logger.warn("mutation-check", "Test suite did not catch injected mutation", { storyId: input.storyId, file: s.file, line: s.line, operatorId: s.operatorId });
    return { success: true, survivors };
  },
};
```

**Integration point:** a new `PhaseKind: "mutation-check"` inserted into `CANONICAL_ORDER` immediately after `"full-suite-gate"` and before `"verifier"`. ### New module layout

```
src/verification/mutation/
  index.ts       barrel
  types.ts       Mutant, MutantOutcome, MutationOperator, SurvivingMutant
  operators.ts   per-language operator tables (TS populated; python/go stubbed empty)
  mutator.ts     generateMutants(changedFiles, language, max)
  apply.ts       applyMutant / revertMutant
  classify.ts    classifyMutant(result): MutantOutcome
```

### Failure Handling

- **Fail-open, always advisory.** The op never returns `success: false`; any internal error is logged and the story proceeds. A surviving mutant is a warning, never a failure.
- **Always revert.** `revertMutant` runs in a `finally` around each mutant's test run, so a thrown `regression` call or a timeout can never leave the working tree mutated.
- **Errored mutants discarded.** A mutant whose re-run yields `ENVIRONMENTAL_FAILURE` / `ASSET_CHECK_FAILED` / `TIMEOUT` is classified `errored` and never reported as a survivor — the false-alarm guard.
- **Opt-in short-circuit.** When `mutationCheck.enabled` is false the op returns immediately, performing zero test runs.
- **Unsupported language no-op.** When `detectLanguage` yields a language with no populated operator table (python, go, undefined), `generateMutants` returns `[]` and the op is a clean no-op.

## Stories

Single-package repo → no `Workdir`. No removal keywords → no terminal-cleanup story. US-002 was split from a single "mutation core" story because it exceeded the project's 10-AC `storySizeGate` cap; the split follows the natural module boundary (generation vs application/classification).

- **US-001 — Config sub-tree** (no dependencies)
  Add `MutationCheckConfigSchema` (`enabled` default `false`, `maxMutants` default `3`, `timeoutSeconds`), mount on `ExecutionConfigSchema`, add the per-package merge spread, and a `reshapeSelector`-based `mutation-check` config selector.
  Context Files: `src/config/schemas-execution.ts`, `src/config/merge.ts`, `src/config/selectors.ts`.

- **US-002 — Mutation generation** (no dependencies)
  Create `src/verification/mutation/` with the shared types, the per-language operator tables (TS populated; python/go stubbed empty), and `generateMutants`. Pure and deterministic — no I/O.
  Creates: `src/verification/mutation/{index,types,operators,mutator}.ts`.

- **US-003 — Mutation apply & classify** (depends on US-002)
  Add `applyMutant`/`revertMutant` (file mutate/restore — **must use Bun-native `Bun.file()`/`Bun.write()`**, never Node `fs`) and `classifyMutant`. Extend the `src/verification/mutation` barrel with these exports.
  Creates: `src/verification/mutation/{apply,classify}.ts`. Context Files: `` `src/verification/mutation/types.ts` — created by US-002, consumed here ``, `` `src/verification/mutation/index.ts` — created by US-002, extended here ``, `src/verification/types.ts`.

- **US-004 — `mutationCheckOp`** (depends on US-001, US-002, US-003)
  Create the deterministic operation wiring the core to `getChangedNonTestFiles` + `selectScopedTests` + `regression`, with DI collaborators, advisory `success:true`, opt-in short-circuit, survivor→warning, and always-revert. Export from the `@/operations` barrel.

- **US-005 — Phase integration** (depends on US-004)
  Register `PhaseKind "mutation-check"` in `CANONICAL_ORDER` after `full-suite-gate`, add its `PHASE_KIND_TO_STATE_KEY`/`InternalBuildState` entries, keep it out of `STRICT_VERDICT_PHASE_NAMES`, add the `addMutationCheck` builder method, and wire `PlanInputs` + `build-plan-for-strategy`.
  Context Files: `src/execution/story-orchestrator/types.ts`, `src/execution/story-orchestrator/builder.ts`, `src/execution/plan-inputs.ts`, `src/execution/build-plan-for-strategy.ts`, `` `src/operations/mutation-check.ts` — created by US-004, integrated here ``.

### Seams

- **US-002/US-003 → US-004.** US-002 exports `generateMutants` and US-003 exports `applyMutant`/`revertMutant`/`classifyMutant` from `src/verification/mutation`. US-004's AC-3 and AC-8 are the behavioral seam anchors: exercising the op through its production path proves it invokes the core (a survivor warning can only arise if `generateMutants → applyMutant → regression → classifyMutant` all ran) and the scoped runner.
- **US-004 → US-005.** US-004 exports `mutationCheckOp` from the `@/operations` barrel. US-005's AC-4 is the seam anchor: with the phase enabled, running the built plan invokes `mutationCheckOp` (spied) after `full-suite-gate`, proving `addMutationCheck` wires the real op into the plan.

## Acceptance Criteria

### US-001 — Config sub-tree

- **AC-1** `[unit]` Parsing the execution config with `mutationCheck` unset yields `config.execution.mutationCheck.enabled === false`.
- **AC-2** `[unit]` Parsing the execution config with `mutationCheck` unset yields `config.execution.mutationCheck.maxMutants === 3`.
- **AC-3** `[unit]` Parsing the execution config with `mutationCheck` unset yields a `timeoutSeconds` that is a positive integer (the schema default).
- **AC-4** `[unit]` Parsing a config where `mutationCheck.maxMutants` is set to `5` yields resolved `maxMutants === 5` (explicit override respected).
- **AC-5** `[unit]` Merging a per-package override `{ execution: { mutationCheck: { enabled: true } } }` onto a root config whose `mutationCheck.enabled` is `false` yields resolved `enabled === true` while `maxMutants` retains its root/default value (field-wise spread merge).
- **AC-6** `[unit]` Applying the `mutation-check` config selector to a parsed config returns an object exposing `enabled`, `maxMutants`, and `timeoutSeconds`.

### US-002 — Mutation generation

- **AC-1** `[unit]` `generateMutants` (importable from `src/verification/mutation`) called with a source containing `a > b` and language `"typescript"` returns at least one `Mutant` whose `after` contains `a < b` and whose `operatorId` names a comparison-flip operator.
- **AC-2** `[unit]` `generateMutants` on a source containing the boolean literal `true` with language `"typescript"` returns a `Mutant` whose `after` replaces that token with `false`.
- **AC-3** `[unit]` `generateMutants` on a source containing `x + y` with language `"typescript"` returns a `Mutant` whose `after` contains `x - y`.
- **AC-4** `[unit]` Each `Mutant` returned by `generateMutants` exposes `file`, `line` (1-indexed), `before`, `after`, and `operatorId` fields.
- **AC-5** `[unit]` `generateMutants` called with language `"python"` returns an empty array (operator table stubbed).
- **AC-6** `[unit]` `generateMutants` called with language `"go"` returns an empty array (operator table stubbed).
- **AC-7** `[unit]` `generateMutants` called with an `undefined` language returns an empty array.
- **AC-8** `[unit]` `generateMutants` given a source with 10 operator-matchable lines and `max = 3` returns at most 3 `Mutant`s.
- **AC-9** `[unit]` `generateMutants` given a source containing no operator-matchable tokens returns an empty array.

### US-003 — Mutation apply & classify

- **AC-1** `[unit]` After `applyMutant(m)` on a temp file the test creates, reading the file back returns `m.after` on line `m.line`.
- **AC-2** `[unit]` Applying then reverting a mutant (`applyMutant(m)` followed by `revertMutant(m)`) leaves the temp file's contents byte-for-byte identical to before the mutation.
- **AC-3** `[unit]` `classifyMutant` given a `VerificationResult` with `status: "TEST_FAILURE"` returns `"killed"`.
- **AC-4** `[unit]` `classifyMutant` given a `VerificationResult` with `status: "SUCCESS"` returns `"survived"`.
- **AC-5** `[unit]` `classifyMutant` returns `"errored"` for a `VerificationResult` whose `status` is each of `"ENVIRONMENTAL_FAILURE"`, `"ASSET_CHECK_FAILED"`, and `"TIMEOUT"`.

### US-004 — `mutationCheckOp`

- **AC-1** `[unit]` `mutationCheckOp`, imported from the `@/operations` barrel, has `kind === "deterministic"`, `name === "mutation-check"`, and `stage === "verify"`.
- **AC-2** `[integration]` Executing `mutationCheckOp` with `mutationCheck.enabled === false` returns `{ success: true }` with an empty `survivors` list and never calls the injected `selectScopedTests` or `regression` deps.
- **AC-3** `[integration]` Executing the op where injected `getChangedNonTestFiles` resolves to one TypeScript source file, its content yields one mutant, and injected `regression` returns `status: "SUCCESS"` → the op returns `success: true` and `survivors` contains one entry whose `file`, `line`, and `operatorId` identify that mutant.
- **AC-4** `[integration]` Same setup as AC-3 but injected `regression` returns `status: "TEST_FAILURE"` → the op returns `success: true` with an empty `survivors` list (mutant killed).
- **AC-5** `[integration]` Same setup as AC-3 but injected `regression` returns `status: "TIMEOUT"` → the op returns `success: true` with an empty `survivors` list (errored mutant discarded, not reported as survived).
- **AC-6** `[integration]` Executing the op for a package whose injected `detectLanguage` resolves to `"python"` returns `success: true` with an empty `survivors` list and never calls injected `regression` (no operators → no mutants).
- **AC-7** `[integration]` With `maxMutants === 2` and a changed file whose content yields 5 candidate mutants, the op calls injected `regression` at most 2 times.
- **AC-8** `[integration]` SEAM: executing the op invokes injected `selectScopedTests` with an input referencing the mutated file and the story's `storyGitRef`, then invokes injected `regression` with the `effectiveCommand` returned by `selectScopedTests`.
- **AC-9** `[integration]` When an injected `regression` call throws, the op still restores the mutated file to its original contents (revert runs in `finally`) and returns `success: true`.

### US-005 — Phase integration

- **AC-1** `[unit]` `CANONICAL_ORDER` contains `"mutation-check"` at the index immediately following `"full-suite-gate"`.
- **AC-2** `[unit]` `PHASE_KIND_TO_STATE_KEY["mutation-check"]` is defined and equals `"mutationCheck"`, and `InternalBuildState` accepts a `mutationCheck` phase entry.
- **AC-3** `[unit]` `STRICT_VERDICT_PHASE_NAMES.has("mutation-check")` is `false` (the phase is advisory, not a strict pass/fail gate).
- **AC-4** `[integration]` SEAM: building a plan via the orchestrator builder with `addMutationCheck(input)` and then running it — with `full-suite-gate` passing and `mutationCheck.enabled` true — invokes a spied `mutationCheckOp` after the `full-suite-gate` phase.
- **AC-5** `[integration]` `build-plan-for-strategy`, given `PlanInputs` that include a `mutationCheck` input, produces a plan whose ordered phases include a `"mutation-check"` phase; given `PlanInputs` without it, the plan contains no such phase.
- **AC-6** `[integration]` A `mutationCheckOp` result carrying a survivor (`success: true`) does not short-circuit the phase loop — the subsequent `verifier` phase still executes.
