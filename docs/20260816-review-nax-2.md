## Findings

### 🔴 HIGH

#### BUG-1: review stage can hang forever on repos with >64KB git output
**Severity:** HIGH | **Category:** Bug (deadlock) | **Status: ✅ VERIFIED**
`src/review/runner.ts:225-236`, caller at `:286`
```ts
const exitCode = await proc.exited;      // line 229 — awaited BEFORE draining
if (exitCode !== 0) return [];
const output = await new Response(proc.stdout).text();
```
**Proof:** `git diff --name-only HEAD` ≥~1,500 modified files (~64KB+ of paths) fills the OS pipe buffer; git blocks writing to the full pipe and never exits, so `proc.exited` never resolves. No timeout exists anywhere on this path (the function has no timer; the caller `runReview` at :286 awaits it directly). This exact hazard is documented and fixed three other places in the codebase — greenfield.ts:53-54, tdd/isolation.ts:50-56, tdd/cleanup.ts:43-45 — all draining stdout concurrently with `exited`. The trigger is deterministic (large diff), not a race.
**Risk:** Indefinite hang of the entire run on large repos.
**Fix:** `const [exitCode, stdout, stderr] = await Promise.all([proc.exited, drain(stdout), drain(stderr)])` and route through `gitWithTimeout` (src/utils/git.ts:69).

#### BUG-2: executor normal path has no deadline on pipe drains
**Severity:** HIGH | **Category:** Bug (deadlock) | **Status: ✅ VERIFIED**
`src/verification/executor.ts:116-117,167`
```ts
const raceResult = await Promise.race([processPromise, timeoutPromise]);
clearTimeout(timer.id);                                  // line 117 — timer disarmed
...
const [stdout, stderr] = await Promise.all([stdoutPromise, stderrPromise]);  // line 167 — unbounded
```
**Proof:** `proc.exited` resolves when the spawned shell exits — **not** when all pipe write-ends close. A test-spawned grandchild (dev server, daemonized process) that inherits the pipe write-end keeps both streams open after the shell exits; lines 94-98's comment documents the codebase's awareness of this exact Bun behavior, and the timeout path caps the drains with `raceWithDeadline(drainTimeoutMs)` (lines 147-150) — but the normal path already cleared the timer and awaits the drains with no bound. Trigger requires the orphaned-grandchild scenario (less likely than BUG-1's, same impact: full run stall, no recovery).
**Risk:** A wedged test run (orphaned child holding pipes) silently wedges the whole pipeline and run.
**Fix:** Apply the same `raceWithDeadline(drainTimeoutMs)` to the non-timeout path (reuse the existing `DRAIN_TIMEOUT` symbol).

### 🟡 MEDIUM

#### BUG-3: stdout/stderr swapped in worktree-removal diagnostics
**Severity:** MEDIUM (downgraded from HIGH) | **Category:** Bug (wrong data in logs) | **Status: ✅ VERIFIED**
`src/execution/pipeline-result-handler.ts:54-58`
```ts
const [exitCode, stderr] = await Promise.all([
  proc.exited,
  new Response(proc.stdout).text().catch(() => ""),
  new Response(proc.stderr).text().catch(() => ""),
] as const);
```
**Proof:** A 3-element tuple destructured into 2 bindings — `stderr` receives the 2nd element (**stdout**), the real stderr (3rd) is discarded. `as const` type-checks cleanly (extra tuple elements are legal in TS destructuring). Impact analysis: the swap only affects the `logger?.warn("Failed to remove worktree directory")` message — genuine git errors are invisible, stdout (usually empty) is logged as stderr. Operation correctness is unaffected, so MEDIUM (not HIGH). Note: `checkpoint/resume-hydrate.ts:53-58` destructures the same 3-element `Promise.all` down to `[exitCode, stdout]`, discarding stderr entirely — but that's a different (harmless, since stderr is unused there) pattern, not a swap; it is not "the correct sibling" as originally claimed here, just a differently-shaped truncation. This finding stands on its own facts at pipeline-result-handler.ts:54-58.
**Fix:** Bind `[exitCode, stdout, stderr]`.

#### SEC-1: URL-userinfo credentials not redacted
**Severity:** MEDIUM | **Category:** Security | **Status: ✅ VERIFIED**
`src/logger/redact.ts:14-68` + `src/quality/runner.ts:101`
**Proof:** Redaction is live on every log call (`src/logger/logger.ts:136` → `redactEntry(rawEntry)`), so gaps matter. `SECRET_KEY_PATTERN` (`/(SECRET|TOKEN(?!s\b)|API_?KEY|PASSWORD|PRIVATE_?KEY|ACCESS_?KEY|WEBHOOK)/i`) contains no `*_URL`/`*_URI`/`*_DSN`/`connectionString` names, and none of the 14 `SECRET_VALUE_PATTERNS` matches `scheme://user:pass@host` (verified each pattern: sk-/ghp_/gh*_/github_pat_/npm_/AKIA/slack/telegram/KEY=value/PEM/JWT/Bearer/Basic/x-api-key). Concrete leak path: `quality/runner.ts:101` logs the full shell `command` string at info — `DATABASE_URL=postgres://admin:secret@db/prod npm run lint` fails both layers (the KEY=value regex requires SECRET|TOKEN|... before `=`, which `DATABASE_URL` doesn't satisfy).
**Risk:** DB/registry credentials leak into JSONL logs.
**Fix:** Add URL/URI/DSN key names to `SECRET_KEY_PATTERN` and a value pattern like `/\b[a-z][a-z0-9+.-]*:\/\/[^/\s:@]+(?::[^/\s@]+)?@/gi`.

#### SEC-2: resolvePermissions fails open to the strongest mode
**Severity:** MEDIUM | **Category:** Security | **Status: ✅ VERIFIED**
`src/config/permissions.ts:39`, `src/config/schemas-execution.ts:188`
**Proof:** `config?.execution?.permissionProfile ?? "unrestricted"` — the undefined-config path resolves to `approve-all`. Schema default is also `"unrestricted"`. (Notably the switch's `default:` case for unknown profile values does fail closed to `approve-reads` — but that's unreachable through the schema.) Every fallback direction for a *forgetting* caller is permissive. Practical exposure today is limited (shipped default is unrestricted), but it becomes HIGH the moment `scoped`/`safe` profiles ship (#374), and it inverts the standard fail-closed convention.
**Fix:** Make the undefined-config default `"safe"` (fail closed); keep fail-open only as the explicit schema default.

#### SEC-3: per-package permissionProfile bypassed on session & complete paths
**Severity:** MEDIUM | **Category:** Security | **Status: ✅ VERIFIED**
`src/agents/manager.ts:630,674,717` + `src/session/manager.ts:444`
**Proof (asymmetry):** `runAs` resolves from `request.runOptions.config ?? this._config` (manager.ts:630) — the per-package effective config threaded at iteration-runner.ts:127-133 — while `runAsSession` (manager.ts:674) and `completeAs` (manager.ts:717) resolve from `this._config` (root) unconditionally, and `SessionManager.openSession` (manager.ts:444) also uses root `this._config`. In a monorepo, a package's `.nax/mono/<pkg>/config.json` `execution.permissionProfile: "safe"` is honored for run-kind ops but ignored for every session turn and `complete()` call — the majority of agent activity. Acknowledged @design at manager.ts:673 ("resolvePermissions needs full NaxConfig").
**Fix:** Thread the effective config (or pre-resolved mode) through `RunAsSessionOpts`/`OpenSessionRequest`.

#### BUG-4: completeWithFallback returns silent empty success when adapter is missing
**Severity:** MEDIUM | **Category:** Bug | **Status: ✅ VERIFIED**
`src/agents/manager.ts:484-491,514-519`
**Proof:** The `!adapter` early return (line 485-492) returns `{ output: "", tokenUsage: {0,0}, estimatedCostUsd: 0 }` with **no** `adapterFailure` and no fallback attempt — and it returns *before* the fail-stale synthesis at lines 514-519 (which only wraps results from `adapter.complete`). `agent.default` accepts any non-empty string (`schemas-infra.ts:278`, no registry membership check), and `getAgent` returns `undefined` for unknown names (registry.ts:102), so `agent.default: "foo"` silently produces empty outputs on every `complete()` path (routing, decompose, etc.) while `runAs` correctly throws `AGENT_NOT_FOUND`.
**Fix:** Throw `NaxError("AGENT_NOT_FOUND")` when no adapter resolves; or run the same empty-output synthesis for the missing-adapter case.

#### BUG-5: worktree git ops have no timeout and leave pipes unread
**Severity:** MEDIUM | **Category:** Bug | **Status: ✅ VERIFIED**
`src/worktree/manager.ts:71,121,146,159,231,272,300` + `src/worktree/merge.ts`
**Proof:** No `gitWithTimeout` usage anywhere in the file (verified via grep — zero hits). Two sites await `proc.exited` without reading or ignoring the pipes at all: `git worktree prune` (:121-126) and `git branch -D` (:146-151) — >64KB of output blocks the child on a full pipe and `exited` never settles. The rest drain concurrently but have no deadline — the repo's own `gitWithTimeout` (utils/git.ts:69, SIGKILL + concurrent drain) is used everywhere else (runner.ts:347, smart-runner.ts:467, bakeoff/preflight.ts:225) with explicit "wedged git (NFS hang)" comments. The worktree paths are precisely the concurrent ones (multi-worktree runs).
**Fix:** Route all WorktreeManager/MergeEngine git calls through `gitWithTimeout`; set `stdout/stderr: "ignore"` where output is discarded.

#### MEM-1: session registry grows unbounded; stuck RUNNING sessions never swept
**Severity:** MEDIUM | **Category:** Memory | **Status: ✅ VERIFIED**
`src/session/manager.ts:364-387,66` + `src/session/manager-sweep.ts:21-32`
**Proof:** `closeStory` (manager.ts:364) transitions sessions to COMPLETED but never deletes `_sessions` entries nor `_liveHandles`. `sweepOrphansImpl` skips every non-terminal state (`if (!terminal.includes(...)) continue;` with terminal = [COMPLETED, FAILED]) — a session stuck RUNNING after a crash (no closeSession ever runs) is never evicted. Stale handle objects and their protocolIds accumulate until the 4h TTL — and only if the process lives long enough to re-run setup (run-setup.ts:361).
**Fix:** Delete entries in `closeStory`; extend the sweep to expire non-terminal sessions older than the TTL.

#### BUG-6: metrics.json read-modify-write is non-atomic
**Severity:** MEDIUM | **Category:** Bug | **Status: ✅ VERIFIED**
`src/metrics/tracker.ts:445-467`
**Proof:** `loadJsonFile → allMetrics.push → saveJsonFile` with no lock. `metricsPathFor` keys off the project (runtime-types.ts:489), so parallel worktree runs (the worktree feature) and concurrent `nax run`s share the file: two processes reading the same base and writing different tails silently drop one run's metrics. Each write is atomic (tmp+rename per `saveJsonFile`), so no corruption — but a lost update.
**Fix:** Serialize with a lockfile, or write per-run files and compact on read.

#### BUG-7: interaction send() has no plugin cascade and no timeout
**Severity:** MEDIUM | **Category:** Bug | **Status: ✅ VERIFIED**
`src/interaction/chain.ts:53-59` + `src/interaction/plugins/telegram.ts:182`
**Proof:** `send()` (chain.ts:53-59) routes only to `getPrimary()` and lets exceptions propagate; `receive()` (chain.ts:65-92) cascades across all plugins — the asymmetry is deliberate for keyboard builds (telegram.ts:156-159) but not for network failures. `sendMessage` (telegram.ts:182) is the only Telegram call without a client-side timeout — verified the siblings: getUpdates (8s), answerCallbackQuery/clearInlineKeyboard/sendTimeoutMessage (4s). A transient Telegram 5xx or hung connection at prompt time aborts the run (send) or blocks it indefinitely (receive never gets called → receive() eventually times out at defaultTimeout, but send() itself aborts).
**Fix:** Give `send()` the same try/catch cascade as `receive()`; add the AbortController pattern to `sendMessage`.

#### BUG-8: auto-pr spawns gh/glab/git push with no timeout and fails open on PR check
**Severity:** MEDIUM | **Category:** Bug | **Status: ✅ VERIFIED**
`src/plugins/builtin/auto-pr/index.ts:32-43` + `forge.ts:36-40`
**Proof:** `defaultRun` (index.ts:32-43) spawns and awaits with no timer/kill — nax-finish's `defaultRun` (index.ts:74-80) has `timeoutMs` + `proc.kill()`, so this is a known, solved pattern not applied here. `hasOpenPr` (forge.ts:36): `if (result.exitCode !== 0) return false;` — any non-zero exit (gh not installed, auth failure, transient API error) is treated as "no PR"; combined with the TOCTOU (no re-check inside `execute()` before pushing), concurrent runs can open duplicate PRs.
**Fix:** Port the timeout/kill pattern; treat non-zero as "unknown → skip with warning"; re-check `hasOpenPr` inside `execute()`.

#### SEC-4: nax-finish telegram notify has no fetch timeout
**Severity:** MEDIUM | **Category:** Reliability | **Status: ✅ VERIFIED**
`src/plugins/builtin/nax-finish/telegram.ts:84`
**Proof:** `sendTelegramNotify` awaits `fetch` with no AbortController — Bun's fetch has no default timeout, and the interaction plugin's Telegram calls all use 4-8s abort timers (this file uses none). It is awaited from the post-run action's notify path, so a hung connection stalls the run's completion phase for the OS TCP timeout (~75s+) or indefinitely.
**Fix:** AbortController + ~5s timer, mirroring the interaction plugin.

#### PERF-1: review iteration store grows quadratically, never pruned
**Severity:** MEDIUM | **Category:** Performance | **Status: ✅ VERIFIED**
`src/review/review-iteration-store.ts:25,37`
**Proof:** `recordReviewIteration` copies prior rounds' full findings (`findingsBefore = prior[prior.length-1].findingsAfter`), `[...prior, iteration]` is O(n) per append → O(n²) per story, and the store (two of them: semantic + adversarial) is never pruned. Long parallel runs (200 stories × 20 rounds × full-text findings) retain tens of MB for the run's lifetime.
**Fix:** Cap rounds per story; store truncated projections (`{id, file, category, severity}`) in `findingsBefore`.

#### PERF-2: test scanner reads unbounded file sizes into memory
**Severity:** MEDIUM | **Category:** Performance | **Status: ✅ VERIFIED**
`src/context/test-scanner.ts:301-304`
**Proof:** `Bun.file(fullPath).text()` with no per-file size cap before regex parsing. The sibling neighbor provider caps at 1MB (code-neighbor-cache.ts:15) — the test scanner doesn't. A 50MB minified/generated test file is fully buffered and regex-parsed.
**Fix:** stat first, skip above ~1MB, mirroring `MAX_NEIGHBOR_FILE_SIZE_BYTES`.

#### BUG-9: non-string PRD dependency entries crash with raw TypeError
**Severity:** LOW | **Category:** Bug | **Status: ✅ VERIFIED**
`src/prd/schema.ts:251-253` (and `:268` for tags)
**Proof:** `validateStory(raw: unknown, ...)` (schema.ts:68) is hand-rolled validation — the story objects are **not** Zod-validated upstream, so `dependencies: ["US-001", 42]` (plausible LLM output) reaches `(rawDeps as string[]).map((dep) => normalizeStoryId(dep))` where `normalizeStoryId` (schema.ts:42) calls `id.replace(...)` → raw `TypeError: dep.replace is not a function`, bypassing the NaxError contract the file enforces everywhere else. **Fix:** Element-type check → NaxError (or skip), same as line 425.
